# Design decisions

Why the engine works the way it does, one decision per row, newest last. A row is never rewritten: a later decision that changes an earlier one gets its own row and names the one it replaces.

| # | Date | Decision | Why | Rejected |
|---|------|----------|-----|----------|
| 1 | 2026-11-06 | **The Ledger history and the revert live in ledger-writer, and an undo is a new commit signed by the asking hireling.** `GET /history?path=&limit=` lists the commits of one page (without a page: the caller's `learnings/<id>/`; a planner sees all of `brain/`); `POST /revert {commit, reason}` reverse-applies a commit, commits it as `<id> <id@hireling.tavern>` (committer `ledger-writer`) and pushes, replaying once on a newer remote. A hireling reverts only commits whose every file is inside its `ledger.write` areas; a planner reverts any page of `brain/`; merges, commits outside `brain/` and reverts that do not apply cleanly are refused (`409`/`422`) and the clone is left clean. The caller is the container name, never the body. | ledger-writer is the only holder of the repo token, so the permission check has to live there. An undo that is a normal commit keeps the history append-only, keeps GBrain's sync simple and leaves a visible `revert(<id>)` next to the original change. | Rewriting history (`git reset --hard` and a force push: destroys the audit and breaks other clones); each hireling cloning and pushing the brain itself (puts the token in every container); revert only through the git host's web UI (no per-area check). |
| 2 | 2026-11-06 | **The gate reads MCP tool names as `mcp__<server>__<tool>`, and only GBrain reads are local.** The single-underscore `mcp_<server>_<tool>` is still accepted. GBrain tools on a fixed read list (`search`, `query`, `get_page`, `find_experts`, `recall`, `entity`, `synthesize`, `context_pack`, `delta`, `get_brain_identity`, `list_skills`) run at once; any other GBrain tool falls through to the profile and tavern-core like an outside action. | Hermes names MCP tools with double underscores, so the old prefixes never matched and every brain read was asked as an external action. Hireling writes go through ledger-writer, so a GBrain write tool is never needed; a read list (not a write list) keeps a tool a newer GBrain adds on the safe side. The read-only token is the second line, not the only one. | Treating every `mcp__gbrain__*` call as local (a newer GBrain with write tools would bypass ledger-writer's checks); matching only the double-underscore form (breaks profiles and logs written with the old names). |
| 3 | 2026-11-06 | **CI tests the Redis-backed stores against a real Redis.** The `go` job starts a `redis:7` service and sets `REDIS_TEST_URL`; each store test package flushes and uses a Redis DB of its own, and skips when `REDIS_TEST_URL` is unset, so `go test ./...` still runs on a laptop without Redis. | The in-memory stores and the Redis stores must behave the same; only a real Redis shows a wrong key, a lost TTL or a script error. | A Redis mock (tests the mock, not Redis); requiring Redis for every local run (blocks contributors without Docker). |
| 4 | 2026-11-06 | **A grant needs the Front Desk's record of the owner's answer.** `POST /actions/answer` takes `agent`; tavern-core looks the decision up in its own Front Desk and grants only when that hireling (`desk_id`) opened it and the owner answered it. It passes the option recorded there, not the body's `choice`, to the card, and the card must be pending for that same hireling (else `403`, the card stays). No Front Desk → `503`, nothing granted. | tavern-core shares the internal network with every hireling and `X-Hireling` proves nothing, so a hireling could post its own "Approve" and grant itself the action the gate had just blocked. Only the owner token can answer a decision on the Front Desk, and the desk lives in the same process, so the proof costs no call and has no configuration to forget. | Trusting the body (the bypass); a signed answer token handed to the runtime (more moving parts for the same proof); waiting for per-hireling tokens on every route (right, and on the roadmap, but the grant could not stay open until then). |
| 5 | 2026-11-06 | **D7 inside a turn: the gate hook cuts a P2/P3 turn once the day's tokens are spent.** Before each tool call of a P2/P3 turn, the hook adds the running turn's spend to today's and asks tavern-core (`tokens` action); over `tokens_per_day` the call is refused with a "wrap up" message. Each turn's priority travels in that turn's context and reaches the hook through the turn file; no priority means P0 (your commands, alerts), which are never cut. | Between-turn holds let one long turn spend many times the budget (a real case: 1.8M tokens against 150k in one turn of 29 tool calls). Carrying the priority per turn (not in a shared field) means a command that takes the turn lock first can never inherit a routine's label, and there is no data race. | Killing the Hermes process mid-turn (loses the answer and the session); a per-turn token cap (cuts P0 work too); a shared "current priority" field (raced: an owner's command ran labelled P3 and was cut). |
| 6 | 2026-11-06 | **Ledger pages pass through the runtime's redactor before ledger-writer, and the redactor knows more credential shapes.** URLs with a password in any scheme, whole PEM private keys, full JWTs, and common key prefixes are masked, besides the values of the container's secrets. | A page is a commit: once pushed it is in every clone and cannot be un-leaked. The runtime's redactor already knows the container's secret values; ledger-writer does not. | A second redactor in ledger-writer (does not know the values); refusing pages with secrets (loses the page for a false positive). |
