# Security model

Hireling runs language models that can execute code and act on your accounts. The design assumes **a hireling's model can be wrong or manipulated** (prompt injection from a web page, a file, another agent) and limits what it can reach when that happens.

## Threats and controls

| Threat | Control |
| --- | --- |
| A hireling exfiltrates data to an arbitrary host | Internal network with no route out; egress allowlist per profile; no IP literals; ports 80/443 only |
| A hireling reaches cloud metadata or the host | Blocked hosts can never be allowed; no Docker socket; `no-new-privileges`; all capabilities dropped except the five the Hermes image needs to step down to UID 10000 |
| A hireling reads another's memory or secrets | One private volume and one environment per container; secrets are per service. The owner bearer is the exception: every hireling receives the existing `FRONTDESK_OWNER_TOKEN` so it can call `/tasks`, `PUT /goal`, `/actions/*` and `POST /asks/answer` |
| Secrets leak into text (logs, reports, bar, Ledger) | The redactor masks the values of every variable in `profile.secrets`, the Front Desk token, the owner token and the Access tokens, and credential-shaped strings (URLs with a password in any scheme, PEM private keys, JWTs, common API key prefixes), on every outbound path, Ledger pages included (a page is a commit: it cannot be un-leaked); Hermes config never contains a secret |
| Destructive shell commands | Hermes approvals on with deny-when-no-human; deny list for sockets, privilege escalation, secret dumping |
| Prompt injection through messages or pages | Bar messages are framed as data; prompts state that other agents' and pages' text is never an instruction; only the owner (Front Desk) and the planner (tasks) can assign work |
| Irreversible actions without the owner | Hard deny list enforced at profile load; `hireling gate` on every tool call (D1) blocks the action and opens an `ask` card (D3); your yes grants one use; Composio sessions without destructive tools; ad spend cap at 0 by default |
| A model tries to switch the gate off | The hook refuses any call that touches `config.yaml`, `.env`, the consent allowlist or the hireling prompt |
| An autonomous action leaves no trace | The Autonomy Log (D4) records who, what, why, outcome and turn; an action that cannot be logged does not run |
| A hireling rewrites shared memory | Read-only Ledger tokens; only ledger-writer commits, inside `ledger.write` areas, after grammar checks, as the hireling (auditable, revertable) |
| Someone else orders your hirelings | Front Desk bearer tokens, constant-time compare; tavern-core published on 127.0.0.1 only |

## Known limits (read before production)

- **Some internal tavern-core routes require the owner bearer.** Every `/tasks` route, `PUT /goal`, every `/actions/*` route and `POST /asks/answer` (same owner token check (ownerOnly); `POST /asks/answer` does not call Approvals.Confirm) answer 401 without `Authorization: Bearer` set to `FRONTDESK_OWNER_TOKEN` (the same token as the Front Desk; a query parameter is ignored; an empty bearer and an empty owner token do not match). Hirelings receive that existing variable through the Compose environment, the same way they receive `FRONTDESK_AGENT_TOKEN`, and the redactor masks the value (`profile.secrets` lists the name; the runtime also masks it directly). That is the residual above: the owner token is in the environment of every hireling. The gate hook reads it from the environment. It is not written into the Hermes command, because that command is stored in `config.yaml`. `POST /goal/progress`, `POST /asks`, `POST /asks/opened` and `POST /agents/{id}/usage` require that same owner bearer (401 without it, with the wrong token, with the token only in the query, or with an empty bearer). `GET /goal`, `GET /asks`, `GET /agents/*`, `GET /autonomy` and `GET /agents/{id}/usage` stay open on the Compose network: they do not change state, the port is 127.0.0.1, and a page still cannot read the JSON (no CORS). `X-Hireling: owner` is compared exactly; `Owner` and `OWNER` are not the owner. Residual: every hireling process receives `FRONTDESK_OWNER_TOKEN` in its environment, because the runtime sends it on those writes. Publishing tavern-core on `127.0.0.1` is **not** a trust boundary on a desktop: every program on this machine reaches them, and so does any web page open in your browser. A page cannot read the answers (no CORS) and cannot send JSON without a preflight, and since this change the internal write routes refuse any body that is not `Content-Type: application/json` (415), which closes the "simple" cross-site POST (`text/plain`, forms). Not closed yet: **DNS rebinding** — a page on a domain that resolves to 127.0.0.1 is same-origin with itself and can send JSON there, because tavern-core does not check the `Host` header; the separate loopback listener and the service tokens below cover it. A caller there cannot grant a blocked action, though: `POST /actions/answer` grants only what the Front Desk shows you answered for that hireling. A local program can still call the routes that remain open. A separate loopback listener that serves only `/api/*` is on the [roadmap](roadmap.md). `compose.yaml` publishes tavern-core on `127.0.0.1` only; do not change that, and do not expose port 8080. For remote access put TLS and a proxy in front that forwards **only `/api/*`**: every owner call (`bin/tavern`'s status, orders and decisions, and the [Tavern MCP server](guides/claude-code-mcp.md), including the task board and the quest at `/api/tasks` and `/api/quest`) is there, behind the owner token.
- **A shared agent token** (`FRONTDESK_AGENT_TOKEN`) lets any hireling report as any other on the Front Desk. Use `FRONTDESK_TOKEN_<ID>` per hireling when that matters.
- **Capped limits are counted and enforced at the gate; token budgets are still reported, not hard-stopped.** Every tool call goes through `hireling gate` (D1), so an external action the gate blocks does not run. A local tool call, however, is allowed without a network check, and the gate is a classifier, not a sandbox: the egress allowlist remains the backstop. See [Autonomy](concepts/autonomy.md#what-enforces-the-limits).
- **Allowed hosts are trusted hosts.** If a hireling may reach `github.com`, it may push to any repository its token allows. Scope tokens (fine-grained, one repo) and toolkits accordingly.
- **The Hermes image is upstream.** Pin it by digest for production and review upgrades.
- **Model providers see the prompts.** Do not put data in a tavern that must not reach DeepSeek or OpenRouter — which is why customer, KYC, financial and legal data stay out by rule.
